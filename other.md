Product Requirements Document (PRD): Image to Post
Огляд продукту
«Image to Post» — це автономний консольний (CLI) інструмент для автоматизованої генерації рекламних постів на основі вхідних зображень з Telegram-бота. Додаток керується через інтерфейс командного рядка, підтримує послідовну обробку черги у фоновому режимі та забезпечує повну ізоляцію даних у робочій директорії запуску.
Цілі та ключові можливості
⚬	Автоматизація створення текстового контенту для соцмереж/реклами на базі мультимедійного вводу.
⚬	Послідовна обробка завдань для уникнення перевантаження API моделей та системних лімітів.
⚬	Можливість запуску декількох незалежних інстансів додатка в різних робочих папках із власними налаштуваннями.
⚬	Збереження стану між перезапусками (resilience & idempotency).
⚬	Проста інтеграція та керування через ШІ-агентів завдяки структурованій довідці (--help) та командам.
Функціональні вимоги
1. Інтеграція з Telegram та авторизація
   ⚬	Генерація та відображення QR-коду в терміналі для підключення сесії Telegram-бота/клієнта.
   ⚬	Збереження токенів авторизації та сесійних даних локально в робочій папці для швидкого перепідключення.
2. Керування чергою завдань
   ⚬	Приймання зображень із чату/каналу Telegram і додавання їх у локальну чергу обробки.
   ⚬	Послідовне виконання: Завдання обробляються суворо по черзі (FIFO, 1 активний процес за раз), без паралельного виконання.
   ⚬	Моніторинг черги: Відображення списку завдань у реальному часі зі статусами (Pending, Processing, Completed, Failed).
   ⚬	Керування: Можливість ручної паузи, відновлення або скасування елементів черги через CLI.
3. Генерація постів та збереження
   ⚬	Виклик LLM/Vision API згідно з заданими промптами, вибраною моделлю, цільовою мовою та обмеженнями довжини тексту.
   ⚬	Структура виводу: Для кожного вхідного зображення створюється окрема піддиректорія.
   ⚬	Всередині директорії зберігаються:
   ⚬	Оригінальний файл зображення.
   ⚬	Текстові файли згенерованих варіантів постів.
4. Збереження стану та відновлення
   ⚬	Автоматична персистентність черги, прогресу та метаданих у робочій папці.
   ⚬	При перезапуску процес зчитує збережений файл стану та відновлює обробку з моменту зупинки без дублювання запитів.
5. Інтерфейс командного рядка (CLI) та логування
   ⚬	Детальний журнал операцій (logs) у консолі та запис у локальний файл логів.
   ⚬	Розширена самодокументована довідка (help), розроблена для легкого парсингу сторонніми ШІ-асистентами та автоматичного заповнення прапорців/параметрів.
   Нефункціональні вимоги та архітектура
   ⚬	Автономність робочої директорії: Усі конфігураційні файли (config.json/.env), стан черги, логи та згенеровані матеріали мають зберігатися виключно у поточній папці запуску (./), а не в глобальній директорії встановлення програми.
   ⚬	Багатоінстансність: Можливість одночасного запуску кількох незалежних процесів у різних директоріях без конфліктів за файлову систему чи сокети.
   ⚬	Формат конфігурації: JSON або YAML для легкого редагування параметрів моделі, промптів і шляхів.
   Який технологічний стек (Node.js/Python/Go) та провайдера AI-моделей (OpenAI, Anthropic, local) планується використати для реалізації?
